# Frontend API requirements: pre-API handoff

## Contract status and reading rules
**Backend operation names below are PROPOSED for agreement.** A01 is an existing static bootstrap-file read, not a new backend endpoint. Semantic backend operation names are not finalized route names. Existing planned URL examples in API_CONTRACT.md remain planned, not implemented ASP.NET endpoints. Most current adapters are mocks/IndexedDB; public runtime configuration and authorized Neshan are the real boundaries currently exercised. No new HTTP client, backend or authentication service is implemented here.

Each operation row supplies feature/action, actor, input, response/UI state and existing adapter. Its group's policy supplies validation, authorization/tenant enforcement, error/retry and idempotency requirements for every row. All inspection operations require trusted tenant + customer/sourceRequest/inspection ownership or staff permission/assignment; IDs/phone/tracking supplied by a browser are never sufficient authority. Backend is REQUIRED for authenticated business operations and cross-device persistence. A01 can remain a static deployment file with no ASP.NET operation; A02 already has a working public loader while cross-device Admin publication still needs the F07 backend. B11 is a real authorized development provider boundary, with the production ASP.NET service still required. Local camera, Blob save, selection, ghost toggles and native playback are not fake API operations.

Common response policy: validate DTO shape and adapt to frontend domain models. Whitelist customer projections; internal notes are never part of them. Support structured 400/422 field/domain errors, 401 authentication/expiry, 403 role/ownership denial, safe 404 invisible resources, 409 version/idempotency conflict, 429 retry guidance and recoverable 5xx/network failures. Do not blindly retry invalid/unauthorized requests. UI shows loading/empty/error/retry without deleting accepted evidence. Agree pagination/filter/cursor semantics, expectedVersion/ETag and server actor/time before integration. No confirmed endpoint contract or SLA is invented.

## C. Evidence and upload lifecycle
Policy C: One kind-aware pipeline for photo and video. Validate kind/requirement/template/revision/request linkage, actual MIME/content/bytes/integrity and expected current revision. Never accept absolute private paths or arbitrary destinations. Tenant/inspection ownership is checked on creation, upload authorization, completion, listing and each media/range request. Stable local job/revision ID maps to one server evidence ID across retries. Completion must be idempotent; checksum/size and server binary acknowledgement are distinct from processing/verification. Temporary upload access must expire and be scoped. Retry transient failures with backoff; refresh upload authorization safely when expired. Clear 413/415/422 and corruption recovery never discards accepted originals.

### Existing media rules versus policy requiring approval
Photo capture emits JPEG; local stores/fixtures may contain other decodable image types (e.g. WebP). The local validator checks image/*, positive size, max 20*1024*1024 bytes; this is not server content sniffing or a binding MIME allowlist. Video MIME preference is VP8 WebM, MP4, generic WebM, then VP9 WebM as actually supported. Video metadata records actual type, byte size, duration and durable Blob key. Local cap is 250*1024*1024 bytes; duration must be finite/positive. Existing configurable 60-second guidance target is not an enforced minimum, maximum or auto-stop. Product/backend must approve binding format/size/duration/quality requirements.

Upload concurrency is 2; upload lease 20s with heartbeat about one third of the lease. Retry policy: retryable attempts below 3, exponential delay from 1s capped at 30s, plus manual retry/retry-all. Resume on app/open-center initialization, online and manual retry. Byte-range resume is not implemented; a file can restart safely. Metadata points to existing Blob keys; no duplicate large video copies/base64 pipeline. Submission/supplemental claims use separate 30s leases. Client MIME/size checks are not cryptographic integrity; agree server hash algorithm/receipt validation and timeout/renewal protocol.

MSSQL stores relative metadata/paths, private filesystem stores binary files under INSPECTION_{InspectionId}. Quarantine incomplete uploads separately; promote only after verified transfer integrity. Reviewer history access is authorized, never a raw filesystem path. No automatic delete on upload/submission. Retention, legal hold, orphan-upload cleanup, allowed export/download and deletion audit require approval.

## D. Summary, submission, status and corrections
Policy D: Reuse capture-package/readiness semantics; all current required media must have binary acknowledgement, but processing is not required to be verified. Odometer is numeric data, not a file. Server must revalidate readiness and immutable submitted snapshot/version. Submit/resubmit/new-attempt commands need persisted idempotency keys and recovery after uncertain responses. Exact correction scope and revision are mandatory; unrelated accepted evidence stays locked. Offline blocks formal submission; no false background success. 409 reloads current version, 422 explains missing requirements, recoverable failures retain data and allow retry.

## E. Reviewer and operational case management
Policy E: Staff session must be server verified; Reviewer queries/mutations require current assignment, not only role. Admin assignment/search stays tenant-scoped. Decisions identify exact current evidence revision and expected case version; whole approval is separate and requires each current required revision/field approved. Reasons required for correction/rejection; actor/time server-issued. Notes are staff-only. Idempotent commands recover duplicate activation, while conflicting commands return 409. Reads may retry; mutations must never replay a different decision. Reassignment/revocation must be checked atomically with decision commit. UI loading/empty/denied/conflict states must preserve case data.

## G. Notifications and brokerage forwarding (server-owned)
Policy G: These are future server operations/events, not browser private-media requests. Tenant-controlled destination allowlist/credentials and authorization are mandatory. Whole approval atomically creates one durable outbox job keyed to approved inspection/version. Delivery uses stable idempotency; receiving brokerage must acknowledge an agreed ID/result. Retry transient timeout/network/5xx failures with capped backoff/jitter and operational visibility; do not endlessly retry invalid credentials/payload or claim success from local completion. Exact attempts/timeouts/retention need backend approval. Uncertain response retries/reconciles the same job. Customer never recaptures solely for delivery failure.

## Ownership, observability and unresolved decisions
API ownership: brokerage ASP.NET inspection services are independent per deployment/database/media root. Shared central Neshan reverse service is global infrastructure. Public Web Map key is not a private service credential. SQL paths and service/auth/forwarding secrets never appear in public runtime settings. Business audit events are server-generated, versioned and access-controlled; client telemetry is not proof of delivery or identity. Never log tokens, raw credentials or private media URLs.

Before coding APIs, agree the semantic operation/DTO routes and OpenAPI generation, sourceRequest/logical-inspection/attempt ID scheme, session topology/OTP role, pagination/version errors, upload hash/MIME/limits/duration/ack protocol, authorized historical media streaming, retention/legal holds, static routing plan, notification copy/consent, forwarding destination/payload/timeouts/idempotency/ack schema and operational escalation. No application code calls invented final endpoints from this document.
